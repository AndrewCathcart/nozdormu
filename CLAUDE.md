# Nozdormu

A Discord bot for an EU guild in World of Warcraft: Forever, Blizzard's "Classic+" (launches 2026-11-04). One always-on Node process holds a gateway connection through discord.js. Andy builds it alone. Work is tracked in GitHub Issues.

## Public repo rules

The code, issues, PRs and Actions logs are all public.

- No secrets anywhere. Config comes from environment variables, validated at startup. Commit `.env.example`; `.env*` is gitignored.
- No real guild data anywhere, including test fixtures, issues and PR descriptions: no real chat, member or character names, channel names, guild Discord IDs, or screenshots. Use made-up data.
- Never log message content. Log IDs and counts instead.
- Andy keeps a private project brief outside the repo. Never commit it or copy its contents in.
- Never fetch Wowhead pages from code; Wowhead blocks it. Link to `https://www.wowhead.com/forever/item=<id>` instead, and never import data copied from Wowhead. The game client's own tables (DB2), as exported by wago.tools, come first: they're Blizzard's data, extracted from the client. Community data is fine where it's accurate: use it only where its licence allows, download it at runtime into Postgres rather than committing it, prefer sources that scan Forever itself (such as Spyglass), and label anything from original Classic (vmangos, pfQuest) as such, since Forever may have changed it. Credit each source, with its licence, in README.md's "Game data" section.

## Stack

Prefer the latest versions that work together, and fast tools. The choices below are current judgement calls, not fixed.

- Node 26, pinned with `devEngines.runtime`; pnpm downloads it to run scripts, whatever Node is installed. pnpm 12, pinned with `packageManager`. Plain pnpm workspaces; no Turborepo or Nx.
- TypeScript 7 (the native compiler), strict. No build step: the code is written so Node can run the `.ts` files directly, so only erasable syntax (no enums, namespaces or parameter properties), and relative imports end in `.ts`. One root `tsconfig.json` covers every package, so a new package can't be skipped.
- Oxlint with type-aware rules for linting, run on TypeScript 7's compiler: the typescript-eslint strict type-checked set, plus exhaustive `switch` checks, consistent type imports and explicit return types on exported functions. oxfmt for formatting. No ESLint or Prettier.
- discord.js 14. Use its types and `discord-api-types` rather than hand-rolled ones.
- pino for structured logging, created with `createLogger()` from core. Code takes a `Pick<Logger, ...>` of the methods it uses (`Logger` is re-exported from core), so tests can pass a typed fake.
- Vitest 5, finding `*.test.ts` files anywhere. Database tests run against real Postgres, not mocks.
- `minimumReleaseAge` in `pnpm-workspace.yaml` refuses packages published less than a day ago. Pin the previous release rather than adding an exclusion. Renovate waits 3 days before proposing an update.
- Postgres on Supabase's free plan, reached through Supabase's session pooler, which supports the prepared statements postgres.js uses. (The transaction pooler would need `prepare: false`.) Drizzle ORM 0.45 with postgres.js, and drizzle-kit 0.31.
- Production is the Supabase project "nozdormu" (eu-west-1) on Postgres 17.6, with automatic RLS on: its `ensure_rls` event trigger enables RLS on every new table. The bot connects as `postgres`, which bypasses RLS, so tables need no policies; RLS with none keeps Supabase's public Data API (the `anon` key) out of them. Match Supabase's major version everywhere, and check nothing needs a newer one.
- Locally, Postgres runs in DBngin, not Docker: the server called "nozdormu" on port 5433, which accepts the `postgres` user without a password. It should run Postgres 17 to match production. Never touch the server on port 5432; it holds Andy's other projects. Only create, use and drop databases whose names start with `nozdormu_`. The bot's local database is `nozdormu_dev`. CI runs a `postgres:17.6` service container on port 5433.
- The Supabase plugin can read the project (`execute_sql`, `list_tables`, `get_advisors`). Use it only to read. Never apply migrations through it, since `pnpm db:migrate` tracks them in the `drizzle` schema and would apply them again.
- zod 4 for env validation. lefthook for git hooks. Renovate for dependency updates.
- Hosted on Railway Hobby. The Claude API writes the weekly digest, through `@anthropic-ai/sdk` with Claude Opus 5.5, from a Claude Console workspace with a monthly spend limit (`ANTHROPIC_API_KEY`). OpenAI's image API paints its picture, called with plain `fetch`, from an OpenAI project with a monthly spend limit (`OPENAI_API_KEY`).

## Architecture

Built so far:

- `apps/bot` is the process. `src/main.ts` loads config (`loadConfig` validates the environment and names bad settings without echoing values), connects to Postgres, builds the features with `createFeatures(createFeatureDeps(...))` (`src/features.ts` lists every feature and builds the real outside-world dependencies they get; `pnpm job --dry-run` swaps some for printing versions), builds the registry, registers commands if they changed since the last start, connects to the gateway, and disconnects cleanly on SIGINT or SIGTERM. `src/migrate.ts` applies pending migrations; Railway will run it before each deploy. Both use `src/startup.ts`, which exits with a message naming the setting when config is invalid, Postgres refuses the connection, or Discord rejects a setting during registration or login. `src/startup-failures.ts` turns Discord's and Postgres's rejections into those messages.
- `packages/core` holds the feature registry (`createRegistry`), the Discord adapters (`registerGuildCommands`, `routeInteractions`, `createChannelPublisher`, `createRecentPostReader`), `registerCommandsIfChanged`, `createLogger`, `serializeError` and `escapeMarkdown`. The channel publisher posts one message at a time, 1.5 seconds apart, so a batch never bursts into Discord's rate limit (about 5 messages per 5 seconds per channel); post through it, never around it. The recent post reader returns the text and card (embed) links of the bot's own messages among a channel's last 50. The registry refuses duplicate command names, dispatches each command (with its options) to its handler, and routes autocomplete requests to the command's `autocomplete`, keeping Discord's limit of 25 suggestions and returning none if suggesting fails. Every dispatch result carries the reply to send: an unknown command or a handler that throws gets a private error reply and a log entry, never a crash. The adapter sends that reply through Discord's interaction callback. Keep the core thin.
- `packages/db` holds the Drizzle schema (`src/schema.ts`), the committed migrations (`migrations/`), `connectDatabase` (which runs `select 1`, so a bad URL fails straight away), `runMigrations` (which returns how many it applied), and the Postgres stores the core needs (`createCommandRegistrationStore`, `createJobRunStore`). A feature's own store lives in the feature package. `@nozdormu/db/testing` gives each test file its own database.
- `packages/core` also holds the scheduler (`startScheduler`). A `Feature` declares its `commands` and scheduled `jobs`, leaving out what it doesn't use. The bot starts the scheduler before it registers commands or logs in (jobs use Discord's REST API, not the gateway), and on shutdown stops it first, then Discord, then the database.
- `packages/ping` is the `/ping` feature.
- `packages/youtube` is the YouTube alert: `parseFeed`, a feed reader that retries YouTube's frequent short outages (bad status, timeout, network error or unreadable feed, 3 attempts 3 s apart), the `youtube.poll` job (every 10 minutes), and the Postgres `SeenVideoStore`. Its first check records the channel's existing videos (and that the check happened, even with an empty feed) without posting. After that, each unseen video newer than the newest one recorded is posted oldest first, and recorded only once its post succeeds, so a failed post is retried at the next check without holding up the others. The first check also stores a baseline, the newest publish time in its feed; an unseen video no newer than that is an old one resurfacing after a deletion, so it's recorded without posting. (Every later upload gets posted and recorded, so a resurfacing video is never newer.) Before posting, the bot reads the channel's last 50 messages and skips any video linked in one of its own, which covers a crash between posting and recording. A failure to post or record one video doesn't stop the others; the check then fails and is logged. Each post carries the nonce `yt-<video id>` with `enforce_nonce`, so Discord drops a repeat sent within a few minutes. Posts never ping anyone (`allowed_mentions: { parse: [] }`).
- `packages/gamedata` is the game database. `/item` suggests items as you type (Postgres trigram search on names containing the text, names starting with it first; deprecated, unused, test, placeholder and "(OLD)" items hidden but still found by ID), then replies publicly with the item's quality, slot, item level, required level and Wowhead link. `/recipe` works the same way for profession recipes and enchants, found by the recipe's name or the name of the item it makes and suggested lowest skill level first (where they turn yellow), so they come in the order you can make them, and replies with what it makes, its reagents, the skill levels where it turns yellow and grey, and the recipe items that teach it, linking the made item, or for an enchant the spell (`https://www.wowhead.com/forever/spell=<id>`). The client data has no required skill for trainer recipes, so none is shown. `/mats` finds recipes the same way and lists everything needed to craft one, optionally several times: the raw materials, totalled, with each crafted reagent broken down into what it's made from all the way down (`GameDataStore.recipesMaking`, a level at a time), then the crafted materials made along the way in the order you'd make them. Amounts are added up across the whole breakdown before working out how often to craft each thing, so a recipe making several at once isn't crafted more than needed. It doesn't break down what transmutes and leather grade-ups make (a Leatherworking recipe named "… Leather" with one reagent), an item that more than one other recipe makes, or an item whose breakdown would need itself. `/train` lists the spells a class learns at a level (the class from a list, the level 1 to 60), linking each spell to Wowhead with its rank and marking race-only spells; at a level with nothing new it shows the next level with new spells, and a list too long for one message ends with how many were left out. The client can't tell trainer spells from class-quest ones (a warrior's Defensive Stance), so the reply says a few come from quests, and it has no trainer costs. The hourly `gamedata.check_build` job downloads each new Forever build's `ItemSparse`, seven recipe tables and seven more for class spells from wago.tools, one at a time and each once (product `foreverProduct`, currently `wow_classic_beta`; only builds 1.60 and later, and only when no table is empty and the build has at least 1,000 items, 1,000 recipes and 500 class spells), and replaces the stored items, recipes and class spells in one transaction (`GameDataStore.replaceBuild`). A class spell is one on a class's own specialisation line (SkillLine category 7 with flag 0x400, which leaves out pet skills; one class in SkillRaceClassInfo), learned by levelling (SkillLineAbility's AcquireMethod 0, and a ClassMask of 0 or one including the class), at its SpellLevels base level, or its spell level where the base is 0. Talents, what talents trigger (SpellEffect), spells hidden from the spellbook (SpellMisc attribute 0x80) and "… Effect" and "… (Passive)" spells are left out. A spell listed twice is shown once, with both entries' races. A race-only spell names only the races that can be its class (ChrRaces and CharBaseInfo), since the client's race masks include later expansions' races. A recipe is a spell on a profession or secondary-skill line (SkillLine categories 11 and 9) with a "create item" effect (24), or an enchant (effect 53, "enchant item"), which makes nothing. Recipes whose item isn't in Forever's item table (mostly Season of Discovery's) are dropped, as are recipe items Forever doesn't have. Each stored build records `importFormat` from `build-check.ts`: when an import starts storing something new, bump it, and the next check imports the current build again. Don't use a data migration for that; the old version keeps running, and importing, during a deploy. Item stats are stored as budget shares, so exact stat values aren't shown yet (see issue #2).
- `packages/dungeons` is `/dungeon`: it suggests Forever's dungeons as you type (every word typed, in any order, ignoring punctuation, with common nicknames such as "brd" and "ubrs" spelled out; all of them, lowest levels first, before anything's typed), then replies publicly with a card for the one picked: its level range (and the level to enter, where known), then a section per boss listing the loot seen from it, one item a line, linked to `https://www.wowhead.com/forever/item=<id>` and, where Spyglass has scanned the item, followed by its slot and kind ("Leather Waist", "One-Hand Dagger", "Bow") and its exact stats in the tooltip's order (damage per second or armour, then Str, Agi, Sta, Int, Spi, then the rest; the wording is in `item-text.ts`). The game stores crit, hit, dodge, parry, block and haste as level 60 ratings (14 crit rating is 1%), so they're shown as the percentages Classic's tooltips give, and it lists each resistance under two names, so it's shown once, with a footer saying loot may be incomplete and has no drop chances. Bosses come in the game's encounter order, which isn't always the order they're fought (Sunken Temple's lists Shade of Eranikus third), so they aren't numbered. When all the loot won't fit on one card (6,000 characters, 1,024 a section, 25 sections), it shows fewer items per boss and how many more. The data comes from Spyglass (MIT, `github.com/Karl-HeinzSchneider/WoW-Spyglass`), an addon whose maintainers scan Forever in game: the `dungeons.sync` job (every 6 hours) reads its `config.json` for the build, lists its files through jsDelivr (GitHub's API allows only 60 requests an hour per IP without a key, and Railway's IPs are shared), downloads each dungeon file and each file of scanned items (up to 10,000 IDs a file, about 23,000 items in all) from GitHub, keeps the dungeons with a level range (the others are Season of Discovery leftovers Forever doesn't have), and replaces the stored dungeons and scanned items in one transaction (`DungeonStore.replaceAll`), unless it found fewer than 20 dungeons or 10,000 items. The client's own tables can't do this: they also list Season of Discovery's instances, and some dungeons only in raid difficulties. There are no drop chances anywhere yet.
- `packages/digest` is the weekly catch-up, so members can see what was said and decided without scrolling back through the chat. The `digest.publish` job runs on Mondays at 09:00 UK time and covers the week before (Monday 09:00 to Monday 09:00). It reads that week's messages from the channels in `DIGEST_CHANNEL_IDS` through Discord's message history when it writes the digest (`createDiscordChatReader`, 100 at a time, needing View Channel and Read Message History), so chat is never stored. It keeps only what people wrote: bots, webhooks, Discord's system messages and messages with no text or attachment are left out. Authors, the people they reply to and anyone they mention go by server nickname. Before reading, it checks the app's flags for the Message Content intent and fails saying so if it's off. A listed channel that isn't a text, announcement or voice channel (a forum, say) fails the run, naming its ID, and threads aren't read. Nickname lookups that fail for any reason but the member having left are logged as `digest.nicknames_failed`. At most the week's latest 400,000 characters of transcript (about 100,000 tokens) go to Claude. `createClaudeWriter` streams one request to Claude Opus 5.5 (effort high, `fallbacks: "default"` so a classifier false positive retries on another model) for the digest as JSON sections (`{ sections: [{ heading, body }], scene, caption }`: Decided, Coming up, Still open, What people talked about, Highlights), and parses the reply itself, so its errors never quote it. `scene` is one specific moment from the week that members will recognise, with its real details, described with fantasy figures by race and class, never members' names or words; `caption` says which moment it is. `createOpenAiIllustrator` draws the scene with OpenAI's `gpt-image-2.5-sunburst` (1536 × 1024, high quality, JPEG; about 40 seconds and $0.04) as a newspaper cartoon with no writing, logging the tokens used and, on failure, only OpenAI's status and error code, since its message can quote the scene. The job won't send OpenAI a scene that names anyone who wrote in the week's chat or was replied to, as whole words in any case (`digest.scene_names_member`). If Claude describes no scene (`digest.no_cartoon`), the scene names someone, or drawing fails (`digest.illustration_failed`), the digest posts without the picture, and if Discord won't take the picture, the masthead goes again without it, with the same nonce (`digest.picture_post_failed`). `renderDigest` posts the masthead giving the week on its own, which carries the picture and, above it, the caption (`captionedMasthead`, at most 200 characters), then the sections in as many messages as Discord's 2,000-character limit needs, splitting between sections, then paragraphs, then words. Posts never ping anyone and show no link previews. A week with no chat gets no digest. What Claude is asked to write is in `prompt.ts`.
- `packages/blueposts` posts Blizzard staff forum posts about Forever in the Forever news channel (`FOREVER_NEWS_CHANNEL_ID`). The `blueposts.poll` job (every 10 minutes) reads the latest posts of two staff groups on the EU forums, the Blizzard tracker and the WoW developers (`https://eu.forums.blizzard.com/en/wow/groups/<group>/posts.json`; the tracker leaves out most developers), and the forum's category names (`/site.json`, looked up again only when a post is in a category it doesn't know). A group's page with no posts fails the check, since it never really happens and would otherwise record an empty first check. It keeps posts in a category whose name, or whose parent's, says Forever, and posts whose topic title does (Blizzard's news announcements sit in General Discussion), matching the capitalised word, so "queue taking forever" doesn't count. Each post is a card (an embed, in Blizzard blue): the poster's name, forum title and avatar, the topic's title linking to the post, the post's opening (HTML turned into text, header-image links and "View Full Article" left out, a video shown as ▶ and its title, cut at a word within 400 characters), whether it's a new topic or a reply and in which forum, and when it was posted. Discord renders markdown in a card's title and description, so those are escaped; the author line and footer show text as it is. It works like the YouTube alert, keeping each forum's history apart by feed name (`eu-forums`) in `blue_post_feeds` and `blue_posts`. The first check posts the latest 3 Forever posts already there, so the channel starts with something in it, and records the older ones without posting them (and doesn't warn of missed posts), storing a baseline just before the oldest post it posts (or, with no Forever posts, the newest post's time); an unseen post no newer than that has resurfaced and is recorded without posting. Other staff posts are recorded without posting too, so a check that has seen none of a group's 20 posts knows more arrived than the page shows and logs `blueposts.gap` for that group. A post is recorded only after it's posted. Before posting, the bot looks among its own recent cards for a link ending in the post's `/<topic id>/<post number>`, which survives a topic being renamed, and each message carries the nonce `blue-<post id>`. A failure to post or record one post doesn't stop the others. Posts never ping anyone.
- `packages/calendar` counts down to Forever's big dates (`foreverMilestones`: launch on 4 November 2026 at 3:00 p.m. PST, and the raids and Onyxia's Lair opening on 9 December, time not yet announced) in the Forever news channel. The `calendar.remind` job (every 5 minutes) posts a week, a day and an hour before a date with a known time, and when it arrives; a week before a date with only a day, and at 09:00 Paris time that day, without claiming a time. Each post shows the date as a Discord timestamp (`<t:…:R>`, `<t:…:F>`), so it reads right in every time zone and however late it goes out. Each reminder is posted once (recorded in `calendar_reminders` after posting, with the bot's recent messages checked first and the nonce `cal-<key>`), and only while it's current: one the bot was down for is skipped once the next is due, and nothing goes out more than 12 hours after a date. The `calendar.events` job (every 6 hours) creates a Discord Event for each coming date with a known time, unless the server has one by that name; the bot needs Manage Events for it. When Blizzard names the raids' time, make them a "time" milestone.
- All tables live in `packages/db/src/schema.ts`, so drizzle-kit sees one schema. A feature's store lives in the feature package and imports its table from `@nozdormu/db`.
- Each feature package exports a factory, such as `createPingFeature()`, that takes the feature's injected dependencies (for example the Discord REST client, the database, the Claude client, a clock) and returns a `Feature`. Command handlers take a parsed `CommandInvocation` and return a `Promise<CommandReply>`. That's the main testing seam.
- Internal packages are source-only: `exports` points at `src/*.ts`, and dependents use `workspace:*`. Shared dependency versions live in the `catalog` in `pnpm-workspace.yaml`.

## Scheduling and time

- The scheduler runs in-process. A job either runs on an interval of 1 ms to about 24.8 days (setTimeout's limit), or weekly at a local time in an IANA time zone (`weekly: { day: "monday", hour: 9, minute: 0, timeZone: "Europe/London" }`), which follows daylight saving. Each job's name is unique (e.g. `youtube.poll`). The weekly arithmetic counts local dates rather than 7 × 24 hours; `latestWeeklyTime` from core gives a job's most recent weekly time. A weekly job never starts before its time by the wall clock, even when Node's timer fires a moment early.
- Before each run, the scheduler claims it in the `job_runs` table: one atomic statement records the start time, but only if the job is due (never ran, or its last run started before a cutoff: one interval earlier, or the latest weekly time). So two processes (say, old and new during a deploy) never both start the same run, and a run that dies halfway isn't repeated until the job is next due. Jobs run at most once per interval or week. The claim isn't a lock: a run still going when the next one is due could overlap it in another process, so keep runs well within their interval. The scheduler logs `job.overrunning` when that happens.
- At startup, an interval job that never ran or fell due while the bot was down is tried straight away; otherwise it waits until one interval after its last start, and never longer than one interval. A weekly job that missed its latest weekly time while the bot was down runs straight away; one that never ran waits for its first weekly time. If the last run can't be looked up, an interval job is tried straight away and the claim decides, and a weekly job looks again a minute later. If the claim itself fails (`job.claim_failed`), the job doesn't run and is tried again an interval later, or a minute later for a weekly job, so a database blip doesn't cost the week.
- A job that throws is logged as `job.failed` and runs again when it's next due: an interval later, or at its next weekly time. Each finished run is logged as `job.finished` with its duration.
- Stopping the scheduler starts no new runs (a claim that comes back after stopping is skipped, so that run is lost, which for a weekly job is that week's), waits up to 10 seconds for runs in progress, then logs `scheduler.stop_timed_out` naming any it gave up on. The bot installs its SIGINT/SIGTERM handlers straight after starting the scheduler.
- The guild plays on EU realms. Server time is one config setting, defaulting to `Europe/Paris`.
- Handlers get the time from the injected clock, never from the system clock directly.

## Database

- Change `packages/db/src/schema.ts`, run `pnpm db:generate --name <what_changed>` (or `--custom` for SQL drizzle-kit can't generate, such as `CREATE EXTENSION`), and commit the generated SQL and its `meta/` files. Never edit a migration that has been merged. Railway's pre-deploy command will apply them after the build and before the new version starts. If a migration fails, the deploy stops.
- Migrations only go forward. Each must work with the code that's already running: add things first, and drop columns in a later PR.
- Database tests use real Postgres, never mocks. At the top of a test file, `const database = useTestDatabase()` (from `./testing.ts` inside `packages/db`, or `@nozdormu/db/testing` elsewhere) gives that file its own database, copied from a template that Vitest's global setup migrates once per run. Use `database.db` inside tests. `useTestDatabase({ migrated: false })` gives an empty one. Global setup also drops test databases more than an hour old, left by killed runs. Tests connect to the server's `postgres` database only to create and drop their own. Unit tests of logic that uses a store may pass an in-memory fake of the store's interface.
- The free plan has no backups. Decide on a backup job before storing anything members type in.
- Free projects pause after a week without database activity.

## Commands

- `pnpm dev` runs the bot against the Dev app and restarts it on changes. `pnpm start` runs it once.
- `pnpm job <job-name>` runs one scheduled job once, outside the scheduler (it doesn't claim the run in `job_runs`), for real, including posting to Discord. `pnpm job <job-name> --dry-run` uses the real feed and database but prints what it would post or record, and changes nothing. `pnpm job digest.publish --dry-run` still asks Claude to write the digest, which costs up to about $0.50, and OpenAI to draw its picture, about $0.04, and saves the picture in the system's temporary folder.

- `pnpm test <path>` runs a single test file. Tests need the DBngin "nozdormu" server running.
- `pnpm db:migrate` applies pending migrations to `DATABASE_URL` and logs how many it applied. `pnpm db:generate` writes a migration from schema changes.
- lefthook formats and lints staged files on each commit.

## Verifying work

Tests are the minimum. Before calling a change done, run `pnpm check` and `pnpm smoke`, and check the change against the real thing.

- Logs are pino JSON lines with a named `event`, plus durations and counts, and never message content or secrets. After a deploy, read them with `railway logs`.
- Log errors under the `err` key, and never log a raw error object any other way. The logger from `createLogger()` passes `err` through `serializeError`, which keeps only the error's name, message, stack, HTTP status, code and (recursively) cause, and an AggregateError's errors. That's because Discord's request errors carry the request URL, which can hold an interaction token, and the request body, which can hold message content. It also replaces the message of Drizzle's failed-query errors, which list the query's parameter values, and of Postgres's data errors (SQLSTATE class 22), which repeat the rejected value.
- Only a real user can run a slash command. Never drive Andy's Discord account in the Discord app or web client; that's a self-bot, which Discord's terms forbid. At milestones, ask Andy to run the command in the test server. You can read back what the bot posted through the bot's own API access. The Developer Portal is fine to drive when Andy asks, but never reveal or copy a token or secret there; Andy handles those.

- After adding a migration, run `pnpm db:migrate` twice against `nozdormu_dev`: the second run must do nothing.

## CI and deploy

- GitHub Actions (`.github/workflows/ci.yml`) runs `pnpm check` on every PR and every push to `main`, in one job with the pnpm store cached. Actions are pinned to commit SHAs, and Renovate keeps them current.
- A ruleset on `main` requires the `check` job to pass, and blocks force-pushes and deleting the branch. Every change reaches `main` through a PR.
- The `image` job builds the `Dockerfile` (the image Railway runs: Node 26, production dependencies only, no build step, Node as PID 1) and applies the migrations from inside it against a Postgres service, twice.
- On push to `main`, once `check` and `image` pass, the `deploy` job runs `railway up --ci --service nozdormu` with a Railway project token (the `RAILWAY_SECRET` secret in GitHub's `production` environment, passed to the CLI as `RAILWAY_TOKEN`), in that environment with a concurrency group. Don't rely on Railway's "Wait for CI" setting instead.
- Railway service settings are set on the service itself, not in the repo: Railway doesn't read `railway.toml` or `railway.json` for new services (Config as Code is deprecated), and its replacement, `.railway/railway.ts`, needs a manual `railway config apply`. Change them with the Railway plugin (`update-service`, or `railway-agent` for regions and draining) and keep this list current:
  - Dockerfile path `Dockerfile`.
  - Pre-deploy command `node apps/bot/src/migrate.ts`; a failed migration stops the deploy and the old version keeps running.
  - Draining seconds 20, so shutdown can finish (the scheduler waits up to 10 seconds for running jobs, then Discord and the database close).
  - Exactly one replica, in Amsterdam (`ams`), near the database. Never run two: both would answer every command.
  - Restart on failure, up to 10 times.
  - No start command: the Dockerfile's exec-form CMD keeps Node as PID 1, so SIGTERM reaches it.
- `railway up --ci` exits once the build finishes, so a green deploy job doesn't mean the bot started. After a deploy, check the deployment's status and logs on Railway (`list-deployments`, `get-logs`): the migrations applied, then `bot.ready`.
- The Railway project and service are both called `nozdormu`, in Andy's personal workspace, with no GitHub connection (CI deploys with `railway up`). The Railway plugin can read them (`describe-service`, `get-logs`); the bot's secret variables are Andy's to set.
